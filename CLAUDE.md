# Seams Club

A social space for the sewing community (feed, profiles, challenges, forum) built on top of a private sewing studio (projects, stash, patterns, measurements). Mobile-first. Public content is readable signed out, like Reddit; interacting needs an account.

The product is called **Seams Club**; internal names (tables, packages, `sewspace_*`) keep the `sewspace` prefix. Don't rename them.

Development happens in this repo; Replit runs and deploys it. Work is done in phases (0–8, see "Build order"); each phase is one commit, then stop for review.

## Stack
- pnpm monorepo, Node 24 on Replit, TypeScript 5.9.
- `artifacts/sewspace`: Vite + React 19 SPA, wouter, TanStack Query, Tailwind 4. Served statically in production.
- `artifacts/api-server`: Express 5, bundled with esbuild to `dist/index.mjs`.
- `lib/db`: Drizzle ORM + Postgres (`pg`). Schema in `src/schema/sewspace.ts`, SQL migrations in `migrations/`.
- `lib/api-spec/openapi.yaml`: **source of truth for the API.** Orval generates React Query hooks (`lib/api-client-react`) and Zod schemas (`lib/api-zod`).
- Auth: Clerk (`@clerk/express` + `@clerk/react`, proxied through `/api/__clerk` in production).
- Files: Replit Object Storage via presigned upload URLs (`artifacts/api-server/src/lib/objectStorage.ts`).
- AI: OpenAI `gpt-5-mini` through `lib/integrations-openai-ai-server` (Replit AI integration env vars).

## Commands
- `pnpm run typecheck` — everything. `pnpm run build` — typecheck + build.
- `pnpm --filter @workspace/api-spec run codegen` — regenerate hooks and Zod after editing `openapi.yaml`.
- `pnpm --filter @workspace/db run migrate` — apply SQL migrations to `DATABASE_URL` (also runs automatically at API startup and in `scripts/post-merge.sh`).
- `pnpm --filter @workspace/db run import-catalog seed/free-patterns.json [--apply | --undo]` — one-off import of free pattern pages (dry run without `--apply`). Runs as the first `ADMIN_USER_IDS` id (or `--as <id>`) under RLS (role `sewspace_app`), so pages belong to that admin; existing designer + name pages are skipped; `--undo` removes only the admin's imported pages nobody else uses yet.
- `TEST_DATABASE_URL=postgresql://user:pass@host:port/postgres pnpm --filter @workspace/db test` — RLS tests (SQL, `lib/db/test/*.test.sql`). The user must be allowed to create databases.
- `TEST_DATABASE_URL=… pnpm --filter @workspace/api-server test` — API tests (`node:test` + `tsx`, `artifacts/api-server/test`). Uses a test-only auth stub (`x-test-user` header) and a fake object store.

## Decisions (agreed with the owner; don't re-ask)
- **Access control:** one server-side module (`artifacts/api-server/src/access/`) decides who can see what; every read goes through it. Postgres row-level security is a second layer: each request runs in a transaction as role `sewspace_app` with `app.user_id` set (`withUser` in `lib/db/src/index.ts`, `scoped()` in `artifacts/api-server/src/lib/scoped.ts`).
- **Migrations are additive only:** no renames, drops or data deletion. New visibility columns default to `private`. Hand-written SQL in `lib/db/migrations/NNNN_name.sql`; keep the Drizzle schema in sync by hand. `drizzle-kit push` is disabled (it would drop policies and views).
- **Never public, whatever the visibility setting:** measurements, pattern PDFs, AI visualisation images. Enforced by upload `purpose` (`pattern_pdf`, `visualization` can never be served to anyone but the owner, and can't be put in image fields).
- **Handles** are owned by Seams Club (not Clerk usernames): 3–30 chars of `a-z 0-9 _ .`, unique ignoring case (`lower(handle)` index), reserved words in `access/handles.ts`. Chosen on Pip's question 1 (`/welcome/1`, `HandleField` under the name).
- **Admin:** Clerk user ids in `ADMIN_USER_IDS` (comma-separated) → `viewer.isAdmin`.
- **Images:** client downscales with canvas before upload (`src/lib/upload.ts`, 1600 px; avatars 512 px; re-encoding strips EXIF/GPS). Post photos are then processed on the server with `sharp` (`api-server/src/lib/images.ts`): EXIF orientation applied, at most 1600 px WebP + 400 px thumbnail, no metadata written (so no EXIF/GPS), dominant colour as a placeholder. `sharp` is externalised in `build.mjs` and resolved from `node_modules` at runtime.
- **AI:** keep OpenAI `gpt-5-mini` via the existing integration. Assistant never available signed out.
- **No demo data** for new users. Existing `is_demo` rows stay as they are and stay private.
- **No private accounts or follow requests in v1:** followers-only content covers it.
- **Ask the owner first** before adding any other dependency or paid service (including image moderation).

## Access rules (current: Phase O1)
**Visibility** (`public` / `followers` / `private`, default `private`) exists on posts, projects (makes), fabrics, threads and patterns. Measurements have none: never shared. (The composer preselects Public for posts; the database default is still private.)

The rule (TypeScript `visibleTo()` in `access/visibility.ts`; SQL `sewspace_can_view()` in migration 0002 — **keep them identical**):
1. The owner always sees their own rows.
2. Private rows: owner only.
3. If the viewer and owner have blocked each other (either direction): nothing, even public.
4. Public: everyone, signed out included.
5. Followers-only: signed-in followers.

- Only owners write, whatever the visibility (RLS `owner_all`; `visible_read` policies are SELECT-only). Projects may only link the owner's own pattern/fabric/thread/measurements, and steps/photos only go on the owner's projects.
- Studio routes (`/api/fabrics`, `/api/projects/:id` …) always filter to the caller's own rows (`own()`); other people's shared items come only through `/api/public/*`.
- Public responses never include `measurementProfileId`, measurement values or `pdfUrl` (`access/makes.ts`).
- Storage downloads return **404, never 403**. File fields may only point at the caller's own uploads (`findForeignObjectField`).
- Posts may only use the author's own media and tag the author's own items (RLS `owner_all` WITH CHECK + API checks). Posting needs a handle and is limited to 30 posts/hour.
- Feeds: Home (`/feed`, signed in, one list, no tabs) = people you follow + you (`homeFeed`); browsing everyone is only Explore = public posts (`exploreFeed`, blocks still apply, `sort=recent|popular`); Saved = your saves you may still see (`savedFeed`). All use `visibleTo` and opaque cursors (`created_at|id`, base64url), 20 per page.
- You only see follows you're part of and blocks you made; `sewspace_blocked_with(other)` answers block checks for pairs that include the caller. The followee may also delete a follow (remove a follower; API not built yet).
- Profiles (Phase 3): `sewspace_public_profiles` hides profiles on the other side of a block, and `sewspace_is_public_avatar` hides their avatar (migration 0004). Header numbers come from SECURITY DEFINER `sewspace_follow_counts(uid)` and `sewspace_followers_only_counts(uid)`, which return numbers only (follows and others' followers-only rows stay unreadable). Posts/makes counts are what the viewer may see; private items are never counted, not even as "locked". Tabs (`access/profile-tabs.ts`): Posts = the person's visible posts; Makes = visible makes, finished first then in progress; Used = visible patterns/fabrics/threads linked from visible makes, each with those makes. An item hidden from the viewer is left out even if the make is visible (stash/patterns default to private, so the Used tab is often empty).
- Social (Phase 4, migration 0005): likes/comments/saves policies read `sewspace_posts` under its own RLS, so "can see the post" is the post rule. Reply depth is checked by a SECURITY DEFINER trigger (`sewspace_comment_check`), not a policy (a policy reading its own table recurses). Counts come from `sewspace_post_counts(ids)`; the viewer's own likes/saves from plain RLS reads. Follows: WITH CHECK requires the followee to be in `sewspace_public_profiles` (has a handle, not blocked either way). A block deletes follows both ways (trigger `sewspace_block_unfollow`). `sewspace_my_blocks()` lists your blocks (the view hides those people). Explore `sort=popular` = most liked public posts from the last 14 days, offset cursor, capped at 500.
- Admin: `withUser(userId, fn, { isAdmin })` sets `app.is_admin`; `sewspace_is_admin()` needs it and a user id. Admins read/resolve all reports and may read and delete only **reported** posts and comments (policies check `sewspace_reports`). Removing closes every open report on the same target; reports keep a snapshot (`snapshot` jsonb) of what was reported. Profiles can only be dismissed. API: `/api/admin/*` behind `requireAdmin` (403); the web page is `/admin/reports`, nav shown when `GET /profile` says `isAdmin`.
- Catalog (Phase 5, migration 0006, `access/catalog.ts`): `sewspace_catalog` rows are shared reference pages (`kind` pattern|product, `slug` = maker + name, unique per kind; creating a duplicate returns the existing page). `created_by` is never sent. Corrections use column-level UPDATE grants, so kind, slug and creator can't change. Your pattern/fabric/thread may set `catalog_id` (`PUT /api/catalog-links/:kind/:id`; patterns → pattern pages, fabrics/threads → product pages). A page shows a make only if the viewer may see the make **and** the linked item (`makesUsing`), so linking never reveals a private item. Review numbers (`sewspace_catalog_stats`) count every review; review lists hide blocked people (RLS + `notBlockedReview`). A review's make must be the author's own (WITH CHECK) and shows only if visible. Reviews are reportable (`target_kind` 'review'); admins delete only reported reviews. Materials on makes and the Used tab carry `catalog` refs. Public URLs: `/catalog`, `/catalog/:kind/:slug` (API-owned prefix for meta tags; `/patterns` stays the private library).
- Challenges (Phase 6, migration 0007, `access/challenges.ts`): slug = lower-case tag (3–30 letters/digits), at most 92 days, must end in the future. The host is a member automatically. Entering needs membership (the API joins you), an active challenge and your own public post (RLS WITH CHECK too). Host removal sets `removed_at`/`removed_by` (column grants only); removed entries are hidden from everyone but the entrant and host, can't be withdrawn or re-entered. Entries follow their post (`visibleTo`), so making the post private hides the entry. Counts (`sewspace_challenge_counts`) are numbers only. Posts carry `challenges` (live entries) and profiles `challengesEntered`. Challenges are reportable (`target_kind` 'challenge', target id = slug); admins delete only reported challenges. Public URLs `/challenges`, `/challenges/:slug` (API-owned prefix for meta tags). The composer enters a post after creating it (`/new?challenge=slug`).
- Forum (Phase 7, migration 0008, `access/forum.ts`): boards `fitting fabric machines patterns beginners mending meetups`, kinds `show_tell question recommendation info poll`. Topics/replies are public except across a block (RLS + `notBlockedTopic`/`notBlockedReply`). `vote_count`/`reply_count`/`last_activity_at` are kept by SECURITY DEFINER triggers and never granted for update; `pinned`/`locked` only change through `sewspace_forum_moderate()` (admins). Authors may update only title/body/tags/accepted_reply_id (column grants); the accepted answer must be a reply in that question (trigger). No upvoting your own posts (RLS). Locked topics take no replies (RLS). Polls: options added by the author; one vote per person, changeable while open (RLS checks the option belongs and the poll is open); results come only from `sewspace_poll_results()`, which hides counts until you vote, unless you wrote it or it closed (the total is always shown). Recommendation replies may name a catalog page (→ "Most recommended"). Topics can link a catalog page (→ "Discussions" on that page) and the author's make (shown only if visible; also "Discussions" on the make page). Show & tell can be shared to the feed as a public post (photos need that). Hot = (votes + 2·replies + 1) / (age h + 2)^1.5, pinned first; offset cursors. The overview's boards carry `latest` {id, title} (most recently active, blocks apply); `listTopics` takes `tag` (exact). Reports: `topic`, `forum_reply`. URLs `/forum`, `/forum/topics/:id` (API-owned prefix for meta tags).
- Drafts (Phase F0, migration 0009, `access/drafts.ts`, `routes/drafts.ts`): `sewspace_drafts` holds one row per (user, kind), RLS `owner_all` only, so nobody else can read, count or change one. `GET/PUT/DELETE /api/drafts/:kind`; PUT replaces. Payload is a JSON object of at most 64 KB measured as jsonb text (same as the table CHECK; 413 over it). Every string in it that starts with `/api/storage/` or `/objects/` must be one of the caller's uploads (`findForeignObjectField`, any purpose), at any depth. Drafts are deleted on submit.
- Post flow (Phase F1, migration 0010, `access/hashtags.ts`): `sewspace_media.alt_text` (≤ 500) and `sewspace_posts.aspect` (`4:5|1:1|original`; new posts default 4:5, posts from before 0010 are `original`, so they look as they did). Display crops with `object-fit: cover` (`aspectRatio()` in `src/lib/hashtags.ts`); stored images are never re-cut. Create and `PATCH /posts/:id` take `aspect`, `altTexts` (only for the post's own photos) and, on edit, `mediaIds` (photo posts: 1–10 of your own, replaces order). Hashtags: parsed from the caption on create/edit (`parseHashtags`, same regex in the web app), lower case, ≤ 30 (400). `sewspace_hashtags` rows are created only by SECURITY DEFINER `sewspace_hashtag_ids()` (no INSERT grant) and readable only once used on a post you may see; `sewspace_post_hashtags` follows its post (owner writes). Counts come only from `sewspace_hashtag_counts(tags)` / `sewspace_hashtag_prefix(prefix, n)`: public posts by people with a handle, minus blocks either way. `GET /api/hashtags/suggest` (signed in): with `q`, top 6 by prefix; without, tags from your own tagged make/pattern/fabric names, the challenge tag and your recent tags. `GET /api/public/tags/:tag` = public posts only (`tagPage`, blocks apply), opaque cursors; `/tags` is an API-owned prefix (meta, sitemap). Post `challenges` carry `entryId` so the author can withdraw in Edit post.
- Project setup (Phase F2, migration 0011): `sewspace_projects.garment` (≤ 40) and `setup` jsonb (`dismissed`, `visibilityChosen`, `stepsChoice` pattern|own|none; projects from before 0011 start dismissed, new ones `{}`); `sewspace_patterns.steps` (array, ≤ 60, never public: public mappers in `access/makes.ts`/`profile-tabs.ts` pick fields explicitly). `PATCH /api/projects/:id/fields` changes only the fields sent (links must be your own: 400 from the API, RLS WITH CHECK underneath; setup flags merge; `status: finished` stamps `completedAt`). `POST /api/projects/:id/steps/from-pattern` appends the pattern's steps and sets `stepsChoice`. Progress is derived from steps on every step change (`recalculateProjectProgress`; 0 with no steps); nothing asks for a % any more. `analyze-pdf` also returns `steps` (same model and request). Pattern `yardage` is read as **yards** (the library labels it so) for the Enough/Short badge.
- Add to stash (Phase F3, migration 0012): `sewspace_fabrics.color_hex` (`#rrggbb`, CHECK) and `sewspace_patterns.format` (`pdf|paper|traced`, nullable). Pattern `difficulty` may be `''` (optional in the flow); thread `brand` and fabric `color` may be `''`. Colour is filled in by the person (owner's call): a name ("Leopard print", "Navy 310") plus an optional closest swatch (`color_hex`); nothing is read from photos (the F3 colour-reading endpoint was removed). Photos are cropped in the browser first (`PhotoCropper`), then upload in the background while the person carries on. No AI here: fabric-type guesses and thread-label reading are **not built** (owner to decide). Public mappers send neither field yet.
- Forum flow (Phase F4, migration 0013): Show & tell needs 1–10 photos (API 400 "Show & tell needs at least one photo."); they go in `sewspace_forum_topic_media` (RLS `owner_all` WITH CHECK: own topic and `sewspace_owns_media`; `visible_read` = topic not blocked) and, with `shareToFeed`, also on a public feed post (same media). Media rows read through policy `topic_read` (SECURITY DEFINER `sewspace_media_on_visible_topic`); files through `sewspace_is_visible_image` (new forum branch) and `shownOnVisibleRow` in `access/objects.ts`. Topics carry `photos` (summaries and pages); older show & tell keeps its photos on the linked post. Feed posts carry `forumTopic` ({id, title, replies}, from `forum_topics.post_id`, same author, not across a block), shown on `PostCard` as "Discussed in the forum". Questions, polls, recommendations and guides never go to a feed. Deleting the topic removes the links, so the files go back to private unless the feed post still shows them. `GET /api/public/forum/similar?q=` ("Already asked?") = up to 3 questions sharing at least 2 title words (stop words dropped, blocks apply). Tags ≤ 5 and polls with 2–6 filled, different options were already enforced (API + `sewspace_valid_tags` CHECK).
- Ideas (Phase S2, migration 0014, `access/ideas.ts`, `routes/ideas.ts`): `sewspace_ideas` (pattern_id, fabric_id, note ≤ 80; both items ON DELETE CASCADE). RLS `owner_all` only; WITH CHECK also requires the pattern and fabric to be the caller's own (checked by `user_id`, since others' public items are readable). `GET/POST /api/ideas`, `PATCH/DELETE /api/ideas/:id` (400 for someone else's item, 404 for someone else's idea); responses carry pattern/fabric name and image. No AI or automatic ideas. `GET /api/projects` also returns `stepsTotal`/`stepsDone` (optional on `Project`) for the progress bars.
- Search (`access/search.ts`, routes in `public.ts`): `GET /api/public/search/posts?q=` (caption contains q, public only, `pagePosts` so `visibleTo` and blocks apply, opaque cursors), `/people?q=` (`sewspace_public_profiles`: handle starts with q (leading `@` dropped) or name contains it; exact handle first; 20; `PublicPerson` fields only), `/tags?q=` (`sewspace_hashtag_prefix`, 10). q is trimmed, at least 2 and at most 80 characters (shorter or invalid = empty result, not an error, because the box searches as you type); `%`, `_` and `\` are literal. Forum and pattern results reuse `listForumTopics?q=` and `listCatalog?q=`. Plain `ILIKE`, no index yet (a trigram index needs the `pg_trgm` extension: ask the owner when it gets slow). `/search` is in robots.txt Disallow.
- Onboarding (Phase O, migration 0015, `access/onboarding.ts`, `routes/onboarding.ts`): `sewspace_onboarding` (spec name `user_onboarding`, named like the other tables): one row per person, `user_id` PK referencing `sewspace_profiles(user_id)` ON DELETE CASCADE; `current_step` 0–8 (0 Meet Pip, 1–7 questions, 8 finished); `goals` ⊆ `stash idea learn share challenges sell`, `experience` ∈ `start couple years pro`, `tools` ⊆ `machine overlocker cover embroidery hand`, `stash_size` ∈ `start drawer cupboard secret` (CHECKs; option ids are the mockup's `renderVals()` values); `completed_at`, `skipped_at`. RLS `owner_all` only. `GET/PATCH /api/onboarding` (PATCH changes only the fields sent; null clears; repeats dropped, order kept), `POST /api/onboarding/complete` (step 8) and `/skip` (answers kept), `GET /api/onboarding/recommendations`. Writes are limited to 120/hour with a counter on the row (`write_count`, `write_window_at`). Name, experience (`EXPERIENCE_LEVEL`: start→beginner, couple→intermediate, years/pro→advanced), favourite things to make (`favoriteGarments`) and default post visibility are saved with `PATCH /profile`, not here. Owner decisions: Q7 saves to the new profile column `default_post_visibility` (public|followers|private, default public = the composer's old preselection; not in the public view); the @handle is asked on the name screen (Q1); the Join page shows Google, Apple and email link/code (the methods on in Clerk); Q4 uses illustrated tiles (mockup photos can't be used). Recommendations (`onboardingRecommendations`): first steps = goals in the order chosen, then Follow 3 sewists / Post your latest make / Add your first 3 fabrics (`firstSteps`; "Set up your pattern shop" is left out while the marketplace is coming soon, `SELLING_OPEN`); 3 shared catalog **pattern pages** (never studio patterns): matching Q4 categories first (`MAKE_CATEGORY`; Costume and Mending have none), then most reviewed; beginner difficulty only when experience is `start` or skipped (fewer than 3 rather than harder ones); one running challenge via `listChallenges` (blocked hosts left out): mending if they make Mending, else a stash one if `stash` is a goal (tag/title match), else most members; null when none run.

App pages under those prefixes (`/posts/:id/edit`, `/forum/new`) get the plain SPA with `noindex` and `Cache-Control: private, no-store` (`sendAppPage`); add any new one there or it 404s in production. In production it reads `artifacts/sewspace/dist/public/index.html` (override with `WEB_INDEX_HTML`; falls back to fetching `/index.html` from the site). In development it fetches Vite's `index.html` and **forwards every other `/@…` path (e.g. `/@vite/client`) back to Vite** — that is why `vite`, `fs`, `id` are reserved handles. Set `PUBLIC_ORIGIN` if canonical URLs should use a custom domain.

## Gotchas
- Route handlers must use the `db` passed by `scoped()` (or `withUser`). Never import `ownerDb`/`pool` in `routes/` — a test enforces this. `ownerDb` bypasses RLS.
- `scoped()` sends the response only after the transaction commits. Don't call OpenAI inside it: read in a short `withUser`, call the model outside (see `/assistant/messages`).
- A Postgres RLS refusal (code 42501) surfaces as 404 via the app error handler.
- **One connection per request transaction:** never `Promise.all` queries on the scoped `db` (pg warns, pg 9 rejects). Await them in turn, or use `sequence([() => q1, () => q2])` from `lib/sequence.ts`. Drizzle builders are lazy, so a list of builders awaited one by one is fine; `.then()` makes them eager.
- Policies on two tables must not read each other (Postgres: "infinite recursion detected in policy"). Use a small SECURITY DEFINER helper instead (see `sewspace_owns_media`, `sewspace_media_on_visible_post` in 0003).
- New public URL prefixes must not be prefixes of app routes (Replit routes by prefix): posts live at `/posts/:id`, not `/p/:id` (which would capture `/patterns`, `/projects`, `/privacy`).
- Page HTML for followers-only content is sent `Cache-Control: private, no-store` and `noindex`; only public pages for signed-out visitors are cacheable.
- When adding a SELECT policy that lets others read a table, re-check every WITH CHECK that used `EXISTS (SELECT … FROM that_table)` to mean "is mine": it now also matches visible rows (migration 0002 had to tighten these).
- In tests, import app code with `await import()` after `./harness`, so `DATABASE_URL` is set first.
- **No type arguments on JSX tags** (`<Toggle<Unit> …>`): Replit's dev-only `@replit/vite-plugin-cartographer` injects attributes after the tag name and the Replit preview fails with "Unexpected token" (production builds are fine). Generic components take `T` from `value` and use `NoInfer<T>` on options/onChange (`Segmented`, `Toggle`, `FilterChips`). Check: run Vite with `REPL_ID=x` and fetch the module.
- Modals: use `useModal` (or `Sheet`/`FlowShell`, which do). It keeps a stack so only the top dialog answers Escape and traps Tab; a hand-rolled `keydown` listener on `window` would also close the dialog underneath.
- Drafts: never autosave until the loaded draft has been applied (`useDraft(..., { active })`), or an empty form overwrites it. Drafts are kept for new items only; edit mode passes `enabled: false`.
- Body parser refusals keep their status (413 too large, 400 bad JSON) instead of becoming 500s (`app.ts` error handler).
- `.field` is unlayered CSS and beats Tailwind padding utilities; inputs with a leading icon use `pl-9`, which has its own `.field.pl-9` rule in `index.css`.
- The SEO router caches `index.html` in production; restart the API after a new web build (Replit deploys do this).
- YAML flow mappings in `openapi.yaml`: quote any description containing a comma or a `#` (a `#` starts a comment), or Orval fails and deletes the generated Zod files.
- `PATCH` bodies for stash/patterns/projects are full objects (spec uses `allOf` of the input schema).
- `@workspace/integrations-openai-ai-server` throws on import without its env vars; tests set placeholders.
- Operations with both path and query parameters get a Zod schema and a TS type with the same name in `lib/api-zod`; re-export the Zod one explicitly in `lib/api-zod/src/index.ts` (see `GetProfilePostsParams`, `GetChallengeEntriesParams`).
- Orval is pinned to emit react-query v5 hooks (`orval.config.ts`).
- There are two `0009_*` migrations (`0009_drafts`, and `0009_forum_tags_check` from the Replit agent, which rewrites the forum tags CHECK with built-in expressions for Replit's Publish schema diff). The runner tracks files by name, so this is fine; never renumber an applied migration.
- The migration runner marks `0000_baseline.sql` as applied on databases created by the old `drizzle-kit push`.
- Emergency rollback for a migration lives in `lib/db/migrations/rollback/` (use with the previous API build).
